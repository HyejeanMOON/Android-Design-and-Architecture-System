# Dependency injection and Hilt

Use this when adding or changing the dependency graph, not for an unrelated screen fix. Android strongly recommends dependency injection, mainly constructor injection. Hilt is a recommended Android implementation when the graph is complex; manual DI remains suitable for a simple app. These are recommendations, not a mandate to replace a working Koin, Dagger, or manual graph.

## Choose and place the graph

- Inspect the existing composition root, graph ownership, DI library, module boundaries, ViewModel factory, scopes, and build compatibility before editing. Keep one clear owner for each binding; avoid a parallel container or hidden service locator introduced for a single feature.
- Inject dependencies through constructors where possible. Compose objects at an app or feature boundary. Use an interface binding only where it protects a meaningful contract or enables substitution; do not wrap every concrete type. Framework-created Android classes may need supported entry-point or field injection.
- Keep business and data classes independent of UI types. A ViewModel receives repositories or needed UseCases, not a Fragment, View, binding, NavController, or Activity Context. A pure domain module need not depend on Hilt or Android just to participate in a graph.
- For a new Hilt graph, use `@HiltAndroidApp` on the application, supported `@AndroidEntryPoint` hosts, and `@HiltViewModel` with constructor injection. Obtain the ViewModel at the correct Fragment, Activity, navigation, or Compose route owner; pass state and callbacks to reusable UI. Do not inject a ViewModel directly as a regular field or give each embedded Compose widget a new owner.
- Prefer `@Inject` constructors for owned concrete types, `@Binds` for an interface implementation, and `@Provides` for third-party or builder-created types. Install a Hilt module in the component that can satisfy its dependencies and matches the intended lifetime. Use qualifiers for genuinely distinct bindings of the same type, such as authenticated and public HTTP clients.

## Lifetime, migration, and verification

- Hilt bindings are unscoped by default. Scope only when an instance must share mutable state, coordinate work, or is demonstrably expensive to recreate. `@Singleton` lasts for the application process, `@ActivityRetainedScoped` survives an Activity configuration change, and `@ViewModelScoped` belongs to one ViewModel. A scope is not persistence across process death. Do not retain short-lived UI or Activity Context in a longer-lived binding; use application context only when its semantics are correct.
- In a legacy XML/Compose app, add Hilt only when the requested change benefits enough to justify plugin, compiler, Application, and host integration. Migrate an explicit vertical slice while preserving existing graph behavior, navigation, and state ownership; do not switch the whole project or toolchain for consistency. Check current AGP, Kotlin, KSP/kapt, JDK, AndroidX, and Hilt compatibility before choosing versions.
- Distinguish ordinary Gradle modules from Play dynamic feature modules. Regular modules can contribute Hilt bindings when visible transitively to the application compilation. Dynamic feature modules have different dependency direction and may require a Hilt `@EntryPoint` plus a Dagger component dependency. Do not add this bridge to ordinary modules or split modules merely for DI.
- Test business classes with constructor-supplied fakes. For Hilt integration tests, replace shared production bindings with `@TestInstallIn`; use a narrower override only when test-specific behavior requires it. Verify graph generation/compilation and relevant startup, ViewModel scope, configuration change, and test replacement paths. Do not claim runtime or leak verification from compilation alone.
